# Предварительный план архитектурного рефакторинга Astro

## Статус документа

Это живой предварительный план. Он задаёт направление и порядок зависимостей, но не является обязательством реализовать все перечисленные классы или этапы буквально. После каждого этапа план пересматривается по фактам из кода, сценариев и профилирования.

Основание плана — [ARCHITECTURE_REVIEW.md](ARCHITECTURE_REVIEW.md). Новые игровые возможности, включая выбор улучшений, ведутся отдельно в [FUTURE_PLANS.md](FUTURE_PLANS.md) и не смешиваются с рефакторингом.

## Цель

Сделать так, чтобы новую механику можно было добавлять одним понятным путём:

```text
input → simulation → events/rules → presentation → verification
```

При этом сохранить существующее поведение, внешний вид и боевые контракты.

## Ограничения

- Не переписывать проект целиком.
- Не вводить ECS или DI-фреймворк как самоцель.
- Не менять баланс одновременно с переносом архитектурной ответственности.
- Не удалять рабочий код до появления проверенного нового владельца его обязанностей.
- Не обновлять визуальные baseline ради прохождения проверки.
- Не объединять несколько независимых архитектурных рисков в один коммит.

## Правила выполнения

Каждая задача проходит одинаковый цикл:

1. Сформулировать сохраняемый контракт.
2. Найти существующие сценарии, которые его защищают.
3. При необходимости сначала добавить минимальную проверку.
4. Изменить одну границу ответственности.
5. Выполнить компиляцию и релевантные сценарии.
6. Для видимых изменений получить и осмотреть PNG.
7. Проверить, не остался ли второй путь выполнения старой логики.
8. Сделать самостоятельный коммит с одной архитектурной причиной.
9. Обновить этот план, если обнаруженные зависимости изменили следующие шаги.

Размер задачи определяется не числом строк, а числом одновременно меняемых контрактов.

## Общие ворота качества

Для любого изменения Java:

```bash
./gradlew core:compileJava
```

Для локального изменения механики запускаются ближайшие logic-сценарии. После изменения общего update/collision/state flow:

```bash
./gradlew desktop:scenarioSuite -PscenarioTags=logic -PscenarioMode=logic
```

Перед завершением крупного этапа запускается полный набор сценариев. Изменения рендера дополнительно требуют визуального сценария, PNG и фактического осмотра изображения.

Готово, когда новый агент может запустить игру и сценарии без чтения исходников.

### 0.2. Зафиксировать карту владения

## Этап 1 — единый поток ввода

Цель: убрать повторную и зависящую от количества fixed ticks обработку управления.

Статус: выполнен 2026-11-23. Ввод фиксируется до simulation loop один раз на render frame; непрерывное управление применяется ко всем fixed ticks через один путь в `PlayState`.

### 1.1. Разделить типы ввода

- Непрерывное состояние: поворот, тяга, стрельба, удержание zoom.
- Одноразовые команды: pause, reset zoom, debug toggle, смена лимита FPS.
- UI-навигация: next/previous/confirm/back/click/scroll.

Результат этапа не обязан быть одним универсальным классом для всех платформ. Важен единый смысл команд.

### 1.2. Ввести снимок управления кадра

Предварительная форма:

```text
InputSnapshot
  held: left/right/thrust/fire/zoom
  pressed: pause/confirm/debug/resetZoom
  pointer: x/y/click/scroll
```

Название и точный API выбираются после проверки Android-ввода.

### 1.3. Оставить один путь применения

- Снимать ввод один раз на render frame.
- Передавать стабильное held-состояние фиксированным тикам.
- Потреблять pressed-команду не более одного раза.
- Убрать вызов `PlayState.handleInput()` из одного из двух текущих путей.
- Не менять ощущение управления и скорострельность.

### 1.4. Проверка

- Один render frame с несколькими fixed ticks не переключает toggle дважды.
- Нулевое число fixed ticks не теряет одноразовую команду.
- Удержание огня и тяги работает при 30/60/120 logic FPS.
- Меню, пауза и настройки работают клавиатурой и мышью.

Контрольная точка: если единый snapshot усложняет Android, сначала вводится нейтральный command-интерфейс поверх существующих адаптеров.

## Этап 2 — явный жизненный цикл экранов и ресурсов

Цель: отделить временный выход с экрана от окончательного освобождения ресурсов.

Статус: выполнен 2026-11-23. `onExit` только деактивирует экран, `onDispose` окончательно освобождает owned-ресурсы; общие шрифты, текстуры частиц и кэш шейдера освобождаются владельцем приложения. Неиспользуемая стековая API удалена, сохранение игровой сессии больше не запускается при входе в паузу.

### 2.1. Расширить контракт состояния

Предварительные события:

```text
enter → active → exit
                  ↓
                dispose
```

- `onEnter/onExit` отвечают за активацию.
- `dispose` освобождает `SpriteBatch`, `ShapeRenderer`, текстуры и другие owned-ресурсы.
- Общие шрифты освобождаются одним владельцем.

### 2.2. Определить семантику модальных экранов

Отдельно решить:

- пауза сохраняет игровую сессию в памяти, но не обновляет её;
- настройки из паузы возвращаются в тот же pause flow;
- фоновый render игры не означает её повторный `enter`;
- `push/pop` либо получает настоящую стековую семантику, либо удаляется как неиспользуемая абстракция.

### 2.3. Отделить сохранение от любого `onExit`

Сохранение должно запускаться политикой сессии в определённых точках, а не автоматически при каждом техническом переходе экрана.

### 2.4. Проверка

- MENU → PLAYING → PAUSED → SETTINGS → PAUSED → PLAYING сохраняет одну сессию.
- Повторные входы не создают дополнительные GPU-ресурсы.
- Завершение приложения освобождает ресурсы всех созданных обработчиков.
- Визуальный фон паузы не изменился.

## Этап 3 — завершить миграцию системы состояний

Цель: оставить один автомат состояний приложения.

Статус: выполнен 2026-11-23. `PlayState` больше не наследует старый экран и не получает nullable `GameStateManager`; старый автомат и недостижимые экраны удалены. `ProgressionManager` сохраняет XP и уровни, но не может открыть отложенный upgrade flow.

### 3.1. Отвязать рабочую игру от старого базового класса

- Убрать зависимость рабочего игрового объекта от старого `gamestates.GameState`.
- Убрать nullable-ссылку на старый `GameStateManager`.
- Сохранить доступ `RealPlayStateHandler` к update/render/session snapshot.

Первоначально класс может сохранить имя `PlayState`, чтобы не смешивать перенос ответственности с массовым переименованием.

### 3.2. Изолировать старую прокачку

- Не реализовывать новый upgrade flow в рамках этого этапа.
- Убрать возможность случайного вызова старого автомата через `ProgressionManager`.
- Сохранить начисление опыта и уровня как рабочие данные сессии.

### 3.3. Удалить доказанно недостижимые состояния

Только после `rg`, компиляции и сценариев рассмотреть удаление:

- старого `GameStateManager`;
- старых `MenuState` и `SettingsState`;
- старого `UpgradeSelectionState`;
- старого базового `gamestates.GameState`;
- `FPSTestState`, если он не имеет отдельной подтверждённой пользы.

### 3.4. Проверка

- В runtime создаётся только один state manager.
- Ни один рабочий объект не получает менеджер состояний как `null`.
- Все маршруты меню/паузы/настроек проходят.
- Полная scenario suite проходит без изменения боевых результатов.

## Этап 4 — отделить игровую сессию от экрана

Цель: сделать состояние текущего забега явным владельцем игровых данных.

Статус: выполнен 2026-11-23. `GameSession` владеет данными забега и детерминированным временем, mapping вынесен в `GameSessionSnapshot`, round-trip защищён logic-сценарием. Snapshot пока предназначен для in-memory восстановления, а не для файловой сериализации.

### 4.1. Определить `GameSession`

Минимальная ответственность:

- игрок и мир текущего забега;
- счёт, уровень и опыт;
- детерминированное время сессии;
- создание snapshot для сохранения;
- восстановление из snapshot.

`GameSession` не должен рисовать UI и обращаться к экранным координатам.

### 4.2. Переместить save/restore mapping

- Не позволять экрану вручную копировать десятки полей.
- Сделать направление `session → snapshot` и `snapshot → session` явным.
- Проверить round-trip сценарием: сохранить, изменить мир, восстановить, сравнить состояние.

### 4.3. Оставить handler координатором

`RealPlayStateHandler` или его будущая замена отвечает за lifecycle экрана и вызывает session update/render, но не содержит механику боя.

### 4.4. Проверка

- Pause/resume не пересоздаёт session.
- Новая игра создаёт новую session.
- Save/restore сохраняет очки, опыт, игрока и активные значимые объекты.
- Сценарии могут создавать изолированную session без полного приложения, если это не ломает visual mode.

## Этап 5 — разделить simulation и presentation

Цель: сделать порядок игровой логики явным, а рендер — побочным представлением состояния.

Статус: выполнен 2026-11-23. HUD и debug overlay вынесены в отдельные renderer-классы и получают immutable view-снимки. `GameWorldRenderer` владеет порядком мировых слоёв и culling-метриками. Камера, фон и визуальные эффекты принадлежат `GamePresentation`, который самостоятельно выполняет их update/dispose. Fixed-tick gameplay pipeline вынесен в `GameSimulation`; `PlayState` остался координатором. Общие `SpriteBatch` и `ShapeRenderer` открываются и закрываются владельцами проходов, а `Player` только рисует в уже открытый проход.

### 5.1. Зафиксировать pipeline симуляции

Предварительный порядок:

```text
spawn/world streaming
→ control and AI decisions
→ movement
→ collision detection
→ collision resolution
→ rewards and gameplay events
→ cleanup/pool return
```

Порядок уточняется по существующим контрактам сценариев.

Фактический порядок после выделения `GameSimulation`:

```text
GamePresentation view update
→ GameSimulation.beginTick:
  session time → controls → world streaming/spawn → scenario beforeUpdate
  → player movement → GameObjectManager update and cleanup
→ GamePresentation effects update
→ GameHudRenderer animation update
→ GameSimulation.finishTick:
  target cache/automatic rocket spawn
  → preliminary player/obstacle collision pass
  → GameObjectManager collision detection and resolution
  → rewards through listeners → scenario afterUpdate
```

Две фазы simulation пока нужны для сохранения наблюдаемого порядка: визуальные эффекты и HUD обновляются после движения объектов, но до targeting/collision. После очистки боевого pipeline эту границу можно упростить. Player/obstacle collision всё ещё имеет два прохода; его устранение относится к этапу 7 и не смешивается с текущим переносом.

### 5.2. Выделить HUD

- Перенести HUD и experience bar в отдельный renderer.
- Передавать ему read-only view данных.
- Не позволять HUD менять gameplay state.

### 5.3. Выделить debug overlay и метрики

- Профилирование не должно размазывать таймеры по игровой механике.
- Debug rendering получает snapshot метрик.
- При выключенном debug не выполняются дорогие вычисления только ради таблицы.

### 5.4. Стабилизировать render-проходы

Целевой порядок:

```text
background
→ filled world geometry
→ line geometry
→ textured/additive effects
→ HUD
→ modal overlay
```

Сущности не должны неожиданно завершать чужой `ShapeRenderer.begin()` или самостоятельно менять глобальный render pass.

### 5.5. Проверка

- Logic mode не зависит от наличия GPU renderer.
- Визуальные сценарии игрока, ракеты, дыма и взрыва совпадают с намерением.
- HUD правильно работает после resize.
- Полная logic suite не изменилась.

## Этап 6 — единая модель владения объектами

Цель: один жизненный цикл для каждого семейства объектов.

Статус: выполнен 2026-11-24. `Player` принадлежит `GameSession`, а `GameObjectManager` хранит его только как прямой collision-индекс. Для остальных gameplay-сущностей wrapper оставлен как runtime handle с типом, внешней командой удаления и индексами менеджера; неиспользуемый `active` удалён, а внутреннее завершение сущности читается тем же `shouldRemove()`. Обычное удаление и полная очистка используют одну точку освобождения. Пули создаются напрямую, авторакеты явно принадлежат пулу, визуальные частицы остаются отдельными presentation-семействами.

### 6.1. Составить окончательную таблицу владельцев

Решить, где живут:

- player;
- bullets and rockets;
- enemies and obstacles;
- gameplay effects;
- purely visual particles.

Допустимо оставить визуальные эффекты отдельно от gameplay objects, если граница выражена явно.

### 6.2. Устранить параллельные update/remove paths

- Один объект обновляется ровно одним владельцем.
- Один владелец решает, когда вернуть pooled-объект.
- `shouldRemove`, wrapper flag и active state не дублируют один и тот же смысл без необходимости.

### 6.3. Решить судьбу `GameObject` wrapper

Варианты оцениваются по фактическому коду:

- оставить wrapper как runtime handle и убрать часть `instanceof`;
- перенести type/capabilities в сами объекты;
- заменить отдельные проверки узкими интерфейсами.

Решение принимается только после двух-трёх конкретных переносов поведения.

### 6.4. Проверка

- Нет двойного update/render игрока.
- Удаление объекта очищает все индексы и возвращает ресурсы один раз.
- Сценарии удаления, награды и продолжения полёта снарядов проходят.
- Статистика active/created/particles остаётся согласованной.

## Этап 7 — разделить столкновения, урон и правила наград

Цель: новые сочетания сущностей не требуют расширять один большой набор ветвлений.

Статус: выполнен 2026-11-24. Все пары обнаруживает единый collision flow `GameObjectManager`; projectile detection формирует `ProjectileCollision`, а resolution отдельно решает owner/friendly-fire, удаление, прямой и splash-урон. `DestructionEvent` содержит цель, источник и причину (`DIRECT_PROJECTILE`, `ROCKET_SPLASH`, `PLAYER_COLLISION`), presentation и reward rules подписаны независимо. Формула очков и опыта живёт в `CombatRewardRules`. Spatial grid не подключался: текущий nested-loop не подтверждён как узкое место.

### 7.1. Единый collision detection

- Убрать отдельную дублирующую проверку игрока в `PlayState`.
- На первом шаге сохранить текущий алгоритм nested loops.
- Формировать понятную пару столкнувшихся объектов или `CollisionEvent`.

### 7.2. Collision resolution

- В одном месте определить исчезновение снаряда, прямой урон, splash и split.
- Не начислять награду внутри геометрического detection.
- Явно сохранить owner/friendly-fire контракты.

### 7.3. Gameplay rules и награды

- Уничтожение создаёт событие с причиной и владельцем урона.
- Счёт и опыт начисляются правилом, а не типовой веткой renderer/manager.
- Разделение астероида и окончательное уничтожение остаются разными событиями.

### 7.4. Spatial grid — только при доказанной пользе

- Сначала измерить стоимость collision phase на репрезентативном количестве объектов.
- Если узкое место подтверждено, подключить уже существующую сетку к detection.
- Сравнить результаты до/после на одинаковом seed.

### 7.5. Проверка

- Полная матрица боевых контрактов проходит.
- Для каждой пары ясно: collision, damage, removal, reward.
- Результат не зависит от порядка коллекций при одинаковом seed, если порядок не является контрактом.

## Этап 8 — способности сущностей и разумная композиция

Цель: уменьшать ложные связи наследования только там, где они мешают новым механикам.

### 8.1. Выделить фактические способности

Кандидаты:

- `Damageable`;
- `Targetable`;
- `RewardSource`;
- `Projectile`/damage payload;
- `CollisionBody`;
- movement/targeting strategy.

Не создавать все интерфейсы заранее. Первый интерфейс появляется, когда одно поведение действительно разделяют несколько несвязанных типов.

### 8.2. Убрать семантическую связь `Asteroid extends Enemy`

Только после появления `Damageable` и `Targetable`:

- обычный астероид остаётся targetable/damageable, но перестаёт называться enemy;
- `EnemyShip` и `OrkAsteroid` получают нужные способности независимо;
- наведение ракеты работает по `Targetable`, а не по базовому классу `Enemy`.

### 8.3. Композиция оружия и поведения

Когда появится реальное повторение, рассмотреть:

- weapon cooldown/fire policy;
- target acquisition;
- health component;
- reward definition;
- particle emitter.

### 8.4. Проверка

- Поведение каждого типа осталось прежним.
- Количество type casts в collision/targeting flow уменьшилось.
- Добавление новой targetable сущности не требует менять существующую иерархию.

## Этап 9 — унифицировать эффекты, пулы и глобальный контекст

Цель: предсказуемая стоимость эффектов и возможность изолировать сессии.

### 9.1. Владение частицами

- Разделить gameplay effects и purely visual effects.
- Для каждого пула определить obtain/init/free contract.
- Проверить бюджет при смерти владельца, culling и очистке сессии.

### 9.2. Сократить глобальное изменяемое состояние

Постепенно передавать владельцу сессии необходимые сервисы:

```text
GameServices or GameContext
  settings
  random/seed
  factories/pools
  logging/metrics
```

Не переносить туда всё автоматически. Размер окна и платформенные API остаются на presentation/application boundary.

### 9.3. Ускорение scenario suite

Переиспользовать процесс только после доказательства, что session, pools, budgets и static state полностью сбрасываются между сценариями.

### 9.4. Проверка

- Последовательный запуск сценариев не меняет их результат.
- ParticleBudget возвращается к нулевому состоянию после очистки.
- Нет повторного dispose или возврата одного объекта в пул дважды.

## Этап 10 — подготовка к будущим фичам

Этот этап не реализует сами фичи. Он проверяет, что архитектура готова принять их без обходных путей.

Контрольные вопросы:

- Можно ли открыть модальный выбор улучшения, не создавая второй игровой мир?
- Можно ли добавить новый `Targetable`, не расширяя цепочку `instanceof` во многих местах?
- Можно ли добавить оружие, не меняя `Player`, collision manager и renderer одновременно?
- Можно ли сохранить и восстановить session через один mapper?
- Можно ли протестировать механику без запуска полного render loop?

Если ответы положительные, архитектурный этап считается достаточным. Дальнейшая абстракция без конкретной фичи не нужна.

## Приоритет выполнения

Ближайший рекомендуемый порядок:

```text
0. Исходная точка
→ 1. Ввод
→ 2. Lifecycle ресурсов
→ 3. Один state manager
→ 4. GameSession
→ 5. Simulation/presentation
→ 6–8. Объекты, collision, композиция

```
