# Архитектурный разбор Astro

## Назначение

Документ описывает текущий рабочий поток игры, сильные стороны, архитектурные риски и безопасный порядок улучшений. Это не план большого переписывания: каждый этап должен сохранять поведение и проходить существующие сценарии.

Подробная последовательность малых задач, проверки и критерии готовности вынесены в [ARCHITECTURE_REFACTOR_PLAN.md](ARCHITECTURE_REFACTOR_PLAN.md).

## Текущий runtime-поток

```text
Desktop/Android/iOS/HTML launcher
    → MyGdxGame
        → TimeManager: накопление времени и фиксированные тики
        → ImprovedGameStateManager
            → MenuStateHandler / SettingsStateHandler / PausedStateHandler
            → RealPlayStateHandler
                → PlayState
                    → Camera + Background
                    → WorldManager: генерация и очистка секторов
                    → Player: управление, движение и собственные эффекты
                    → GameObjectManager: объекты, обновление, столкновения, награды
                    → отдельные коллекции частиц и эффектов
                    → HUD и игровой рендер
        → render текущего состояния
        → сброс состояния ввода
```

Порядок одного обычного кадра:

1. `MyGdxGame` получает реальный `deltaTime`.
2. Накопитель выполняет от нуля до нескольких фиксированных обновлений состояния.
3. После фиксированных обновлений состояние ещё раз обрабатывает ввод.
4. Текущее состояние отрисовывается; пауза отдельно рисует замороженную игру как фон.
5. Сбрасываются края клавиш и обновляются метрики.

## Что уже сделано хорошо

- Фиксированный шаг отделяет скорость механики от частоты рендера.
- Платформенные launcher-модули не содержат игровую механику.
- `ImprovedGameStateManager` даёт единый внешний вход для экранов приложения.
- `GameObjectManager` уже централизует регистрацию, удаление и большую часть столкновений.
- Боевые контракты защищены детерминированными сценариями, поэтому внутреннее устройство можно менять небольшими шагами.
- Визуальные и логические сценарии используют один игровой код, а не копию формул.
- Пулы и бюджет частиц показывают правильное направление для дорогих краткоживущих объектов.

## Главные архитектурные напряжения

### 1. Незавершённая миграция состояний

Рабочий внешний автомат — `ImprovedGameStateManager`, но `PlayState` по-прежнему наследуется от старого `gamestates.GameState` и принимает старый `GameStateManager`. Меню и настройки старой системы остаются в репозитории, хотя обычный запуск их не использует.

Важно: удалять весь пакет `gamestates` нельзя. `PlayState` сейчас является реальным игровым ядром. Сначала нужно отвязать его от старого базового класса и менеджера; только затем удалять доказанно недостижимые экраны старой системы.

### 2. `PlayState` совмещает слишком много ролей

В одном классе находятся создание сессии, игровой порядок обновления, камера, ввод, мир, спавн ракет, частицы, прогрессия, столкновения игрока, HUD, debug UI, профилирование, сохранение и восстановление. Большой размер — следствие смешанных причин изменения, а не самостоятельная проблема.

Целевая граница:

```text
Play screen / handler       жизненный цикл экрана и переходы
GameSession                состояние текущего забега
GameWorld                  сущности и упорядоченное обновление систем
WorldRenderer              мировые render-проходы
HudRenderer                экранный интерфейс
SaveGameMapper             snapshot ↔ session
```

Названия предварительные. Выделять классы следует только по одному рабочему срезу, а не создавать пустой каркас заранее.

### 3. Ввод обрабатывается в двух местах

`PlayState.update()` вызывает `handleInput()` на каждом фиксированном тике, а `RealPlayStateHandler.onHandleInput()` вызывает его ещё раз после тиков кадра. Непрерывные команды обычно переживают это, но edge-команды могут сработать несколько раз при догоняющих тиках или не в том порядке.

Желаемый поток:

```text
OS input → один InputSnapshot/набор команд на кадр
         → фиксированные тики читают стабильное состояние управления
         → одноразовые команды потребляются ровно один раз
```

### 4. Смешаны несколько моделей объектов

- `Player` обновляется отдельно.
- Большинство мировых объектов обновляет `GameObjectManager`.
- Часть частиц хранится в `PlayState`, часть — в менеджере, часть — внутри сущностей.
- `GameObject` одновременно использует `Type`, интерфейсы и проверки `instanceof`.
- Пространственная сетка строится в `WorldManager`, но основные столкновения всё ещё проходят вложенными циклами в `GameObjectManager`.

Следствие — трудно однозначно ответить, кто владеет объектом, кто его обновляет, рисует, удаляет и возвращает в пул.

Для каждого типа должен существовать один владелец и один путь жизненного цикла:

```text
create → register → update → collide/resolve → mark/remove → dispose or return to pool
```

### 5. Столкновения и последствия связаны

`GameObjectManager` одновременно находит пересечения, определяет типы через cast/`instanceof`, наносит урон, разделяет астероиды, создаёт splash-урон и уведомляет о наградах. Отдельная проверка столкновения игрока с препятствиями остаётся и в `PlayState`.

Полезная граница без полноценного ECS:

```text
CollisionDetection → CollisionEvent
CollisionResolution → damage/remove/split/explosion
GameRules           → score/experience/reward
```

Это позволит тестировать правила отдельно и не размножать комбинации типов в одном методе.

### 6. Жизненный цикл ресурсов не выражен контрактом

У `StateHandler` есть `onExit`, но нет `dispose`. Выход с экрана и окончательное освобождение `SpriteBatch`, `ShapeRenderer`, текстур и шрифтов — разные события. Сейчас менеджер очищает обработчики, не вызывая их отдельное освобождение ресурсов.

Нужны разные понятия:

- `onEnter/onExit` — временная активация экрана;
- `dispose` — окончательное освобождение GPU/нативных ресурсов;
- `suspend/resume` или модальный стек — если экран должен сохраниться под другим.

### 7. Глобальное изменяемое состояние усложняет изоляцию

Размер окна, камера, рекорд, настройки, пулы, бюджет частиц и scenario runtime во многом статические. Это удобно на раннем этапе, но мешает переиспользовать один процесс для нескольких независимых сессий и делает зависимости неявными.

Не нужно сразу вводить DI-фреймворк. Достаточно постепенно передавать явный `GameContext`/`GameServices` владельцам сессии и оставлять платформенные глобальные значения на внешней границе.

## Наследование и композиция

### Где наследование оправдано

- Общая позиция, скорость, форма и базовая геометрия мирового объекта.
- Семейство частиц с действительно одинаковым жизненным циклом.
- Общий контракт состояния экрана, если остаётся только одна система состояний.

### Где текущая иерархия вводит в заблуждение

`Asteroid extends Enemy` позволяет переиспользовать здоровье, но астероид не является врагом в предметном смысле. Из-за этого поиск целей и правила наград вынуждены дополнительно различать `obstacles` и `enemies`.

Лучше выразить способности отдельно:

```text
SpaceObject
  + Health / Damageable
  + CollisionBody
  + Targetable
  + Reward
  + Movement/AI
```

Это не требование немедленно строить ECS. На Java достаточно небольших интерфейсов и объектов-компонентов там, где поведение реально меняется независимо.

### Практическое правило

- Наследование отвечает на вопрос «является ли объект разновидностью базового объекта?».
- Композиция отвечает на вопрос «какими возможностями и изменяемым поведением объект обладает?».
- Если базовый класс требует от менеджера цепочку `instanceof`, полиморфный контракт либо выбран неверно, либо недостаточен.

## Целевой игровой flow

```text
1. Input collection
   Снять состояние управления и одноразовые команды.

2. Fixed simulation tick
   Spawn → AI/targeting → movement → collision detection
         → collision resolution → rewards/events → cleanup.

3. Presentation update
   Камера, HUD-анимации и визуальные эффекты, не влияющие на механику.

4. Render
   World passes → effects → HUD → modal UI.
```

Порядок фиксируется как контракт. Система не должна зависеть от того, в каком месте большого метода случайно добавлен новый блок.

## Безопасная дорожная карта

### Этап A — закрепить границы без изменения поведения

1. Актуализировать документацию и пометить старые планы как исторические.
2. Зафиксировать runtime-поток и владельца каждого семейства объектов.
3. Устранить двойную обработку ввода, сохранив управление сценариями.
4. Добавить `dispose` в жизненный цикл экранов и проверить ресурсы.

### Этап B — завершить миграцию состояний

1. Отвязать `PlayState` от старого `GameState`/`GameStateManager` без изменения механики.
2. Переименовать его в соответствии с оставшейся ролью только после выделения границ.
3. Удалить старые меню, настройки и автомат состояний после доказательства отсутствия ссылок.
4. Заменить особые условия `underlayState` единым правилом модальных экранов или простым стеком с корректным lifecycle.

### Этап C — разделить игровой цикл

1. Выделить snapshot ввода.
2. Выделить `GameSession` как данные текущего забега и точку сохранения.
3. Перенести HUD/debug rendering из симуляции.
4. Свести столкновения игрока к единому collision flow.
5. Подключить пространственную сетку только после сравнительного измерения.

### Этап D — упростить модель сущностей

1. Определить единый контракт update/render/removal.
2. Убрать дублирование `Type` и `instanceof` по одному поведению за раз.
3. Отделить `Damageable`, `Targetable`, `Reward` и оружие там, где это сокращает реальные ветвления.
4. Унифицировать владение частицами и возврат в пулы.

## Процесс архитектурных изменений агентами

Для каждого небольшого рефакторинга:

1. Записать сохраняемый поведенческий контракт.
2. Найти сценарии, которые его защищают; при пробеле добавить минимальный сценарий до изменения.
3. Изменить одну границу ответственности, не смешивая с новой фичей и визуальным редизайном.
4. Запустить близкие logic-сценарии, затем полный набор затронутых тегов.
5. Для render/UI изменений осмотреть фактический PNG.
6. Проверить diff на второй параллельный путь и устаревшие комментарии.
7. Делать небольшой самостоятельный коммит, который можно безопасно откатить.

Архитектурное решение считается полезным, если после него проще ответить хотя бы на один вопрос: кто владеет данными, где меняется состояние, в каком порядке идёт обработка, как это проверить и как добавить соседнее поведение без копирования.

## Чего пока не делать

- Не переписывать игру целиком и не вводить ECS ради самого ECS.
- Не удалять `PlayState`, пока его рабочие обязанности не перенесены и не защищены сценариями.
- Не объединять архитектурный рефакторинг с балансом или новой прокачкой.
- Не оптимизировать столкновения через spatial grid без измеримого узкого места.
- Не создавать интерфейс или builder после одного случая; сначала дождаться повторения.
